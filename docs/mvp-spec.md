# linkops-lite MVP Spec(v0.3)

> 2026-11-04 定稿草案。只管"外链功能能用",不考虑学习路线。
> 确认后替代 `design.md` 中与本文冲突的部分(`design.md` 的研判口径、档位规则继续有效)。

## 1. 目标与成功标准

**一句话:** 给一个自有站,从外链库里挑出能留链接的入口,AI 判断并起草要提交的内容(博客评论或表单填写包),我逐个打开、粘贴、点提交,之后回查链接是否真的出现。

**MVP 能用的标准:**
- 为一个站建 50 条的批次,批量研判 10 分钟内跑完;审核 15 分钟内审完。
- 每个通过的入口都有可直接使用的内容:博客评论是一条和文章相关的评论;表单是按字段列出的值。每项可一键复制。
- 提交队列连续处理,每条 ≤ 1 分钟。
- 提交过的入口可一键回查:链接是否公开、是否 nofollow。
- 任意时刻能看到每个入口对这个站的状态,并导出 CSV。

## 2. 范围

| 做(MVP) | 不做(记到 ideas.md) |
|---|---|
| 单用户、本机运行、无登录 | 多用户、账号体系、部署上线 |
| 渠道 1:**博客评论**(先做,优先标准 WordPress 评论表单) | 社区发帖、资源页联系、投稿 |
| 渠道 2:**提交表单**(目录、产品展示、链接目录) | |
| 人工打开页面、人工点提交 | 浏览器扩展自动填表、自动点提交、绕验证码、换身份重试 |
| 回查链接是否公开、rel 属性 | Google 是否收录、排名影响 |
| 研判前只用确定性筛选 | 向量粗筛、RAG、MCP |
| Spring Boot 静态 HTML 页面 | 独立前端工程、页面美化 |

## 3. 主流程

```
① 外链库 → ② 站点配置 → ③ 建批次
                              ↓
⑥ 起草内容 ← ⑤ 审核 ← ④ AI 研判
   ↓
⑦ 手动提交 → ⑧ 回查生效 → ⑨ 进度追踪
```

| 步骤 | 输出 | 谁做 |
|---|---|---|
| ① 外链库 | `backlink_source`,带可访问状态和渠道类型 | 已有,补渠道分类 |
| ② 站点配置 | `site`:域名、联系人、联系邮箱、介绍、资料包、事实清单、重要页面 | 我 |
| ③ 建批次 | `batch` + 一批 `candidate` | 我点按钮 |
| ④ AI 研判 | 每个候选一条 `judgment` | 系统批量 |
| ⑤ 审核 | 候选 approved / rejected | 我 |
| ⑥ 起草内容 | 每个候选一份 `draft`:评论稿或填写包 | 系统批量,我可改 |
| ⑦ 手动提交 | `submission`:submitted / abandoned / skipped | 我 |
| ⑧ 回查生效 | `link_check`:live / pending / missing / page_gone | 系统,我触发 |
| ⑨ 进度追踪 | 列表 + CSV | 系统 |

## 4. 功能明细与验收

### F1 外链库(已有,补两项)
- 已有:导入、规范化去重、可访问性检查。
- 补:渠道类型 `channel`(blog_comment / submit_form / other / unknown)。导入时可指定;未指定的在可访问性检查时按页面粗判(有 WordPress 评论表单 `#commentform`/`comment` 字段 → blog_comment;有 URL 字段的 form → submit_form),不调用模型,我可手动改。
- 补:列表页按状态、渠道、关键词筛选。
- **注意:** 现有 699 条基本是目录类,博客评论需要另外导入文章 URL 列表(每行一个文章地址即可)。
- 验收:导入一批文章 URL 后,能按渠道筛出 blog_comment。

### F2 站点配置(每个站独立)

| 字段 | 用途 | 必填 |
|---|---|---|
| 名称、域名、首页 URL | 识别、回查时匹配链接 | 是 |
| 联系人 | 评论署名、表单 Name 字段 | 是 |
| 联系邮箱 | 评论和表单的 Email 字段;只存本机库,导出时脱敏 | 是 |
| 站点介绍 | 研判判断相关度 | 是 |
| 一句话 / 短描述(≤160)/ 长描述(≤500) | 表单填写 | 是 |
| 分类候选、标签、定价 | 表单填写 | 分类、定价必填 |
| Logo / 截图 URL | 表单填写 | 否 |
| 事实清单 | 起草只能引用这里的事实 | 是 |
| 重要页面(URL + 一句话) | 博客评论选择链接到哪一页 | 否,至少有首页 |

- `sites/*.md` 文件读取改为读库。
- 验收:页面上新建、编辑站点;两个站的配置互不影响。

### F3 建批次
- 选站点 + 渠道(blog_comment / submit_form)+ 可访问状态(默认 ok)+ 数量上限(默认 50)。
- 自动排除:这个站已经有候选的来源。
- 验收:显示入选数量、被排除数量及原因。

### F4 AI 研判(在现有预览上补齐)
- 复用现有研判:关闭思考、temperature=0、结构化输出、业务校验、反馈重试、prompt 版本。
- 博客评论增加判断项:评论是否开放、是否有 Website 字段、是否明显禁止留链接、评论区是否被垃圾评论淹没、文章与站点的相关度(只影响档位:相关 → HIGH/MEDIUM,不相关 → LOW,仍为 SUITABLE)。用独立的 prompt(`prompts/judge-comment/<版本>/`)。
- 补:批量执行(并发 5)、结果入库、单条重试、批次进度、单批次 token 上限 40 万,超限暂停。
- 验收:50 条跑完,失败有原因;重跑新增一条 judgment,列表显示最新一条。

### F5 审核台
- 默认排序:SUITABLE(HIGH → MEDIUM → LOW)→ UNCERTAIN → UNSUITABLE。
- 每行:网址(新标签打开)、渠道、结论、档位、首条理由、风险;可展开。
- 通过 / 拒绝,支持批量勾选,可加备注;UNCERTAIN 可直接通过。
- 验收:50 条 15 分钟内审完,刷新后状态保留。

### F6 起草内容

**博客评论(先做):**

目标:让站长愿意保留这条评论。链接主要靠 Name 和 Website 字段展示,正文首先是一条对文章有价值的评论。

- 输入:文章标题、正文摘要、已有评论的语气(如能抓到)、站点配置。
- 先判断**切入方式**(写进草稿,审核时可见):
  - `related`:文章内容和站点功能有自然关联(社交媒体简介、标题排版、手工/卡片、设计、学生作品等)→ 正文可以用一句话自然提到站点能做什么,不放链接、不带推销语气。
  - `unrelated`:没有自然关联 → 正文**完全不提站点**,只回应文章;站点只通过 Name 和 Website 字段出现。
- 输出:评论正文(40–100 词,语言跟随文章)、Name(默认联系人,可配置为"联系人 + 站点名"等格式)、Email、Website(相关时从重要页面选最相关一页,不相关时用首页)、切入方式及理由、引用的事实。
- 写法(对页面友好):
  - 回应文章里的具体内容:引用一个细节、补充一个想法或提一个真诚的问题。
  - 语气贴合文章和评论区;不用"Great post!"之类通用夸奖,不用营销词。
  - 正文不放任何 URL;不编造使用经历、数据和客户;提到站点时事实只来自事实清单。
- 校验:字数范围;正文无 URL;`unrelated` 时正文不出现站点名和域名;不出现事实清单以外的站点功能;和同站点最近的评论相似度不过高(避免模板化)。

**提交表单:**
- 重新抓表单字段,模型把字段映射到站点配置。
- 输出:字段 → 值 → 来源;识别不了的字段列为"需人工";页面上的提交要求。
- 字数超限时改写描述并标"已改写"。没有可识别表单时只给通用资料包,标"需人工找入口"。

- 两种草稿都可在队列页手动修改,保存修改后的版本。
- 验收:各抽 10 份,可直接使用的 ≥ 8 份;没有资料以外的事实。

### F7 提交队列
- 一次一条:目标网址按钮、草稿各项(每项复制按钮)、注意事项。
- 标记:已提交 / 放弃(原因:需付费、需登录、验证码、评论已关闭、入口失效、其他)/ 稍后。
- 标记后自动进入下一条。
- 验收:连续处理 10 条不离开队列页(除了打开目标站)。

### F8 回查生效
- 对象:已提交的候选。
- 动作:抓取提交页面(博客评论 = 文章页;表单 = 提交后的列表页或我填的"公开页面 URL"),查找指向本站域名的 `<a>`。
- 结果:
  - `live`:找到链接,记录 href、rel(nofollow / ugc / sponsored / 无)、锚文本
  - `pending`:没找到,距提交不足 7 天(博客评论通常要审核)
  - `missing`:没找到,距提交已超过 7 天
  - `page_gone`:页面 404 或打不开
- 触发:按站点"回查全部到期的",或单条回查;每条保留回查历史。不自动定时(MVP 手动触发)。
- 验收:手动在一个测试页面放入本站链接,回查能识别出 live 和 rel。

### F9 进度追踪
- 按站点看所有候选:渠道、状态、研判结论、提交时间、最近回查结果。
- 统计:已提交数、live 数、其中 dofollow 数;博客评论按切入方式(related / unrelated)分开统计 live 率。
- 导出 CSV(UTF-8 BOM,表格软件不乱码)。

## 5. 候选状态

```
new → judged → approved → drafted → submitted → live / missing / page_gone
                   ↘ rejected            ↘ abandoned / skipped
judge_failed / draft_failed(可重试)
```

"已提交"只表示我点了提交;"live"只表示页面上能看到链接,不代表 Google 已收录或有排名效果。

## 8. 安全与约束

- 第三方页面内容只当数据,不执行其中的指令。
- 不自动点提交、不处理验证码、不换身份。
- 联系邮箱只存本机开发库;日志不打印邮箱和草稿全文。
- 回查请求限速(同一 host 间隔 ≥ 2 秒),使用通用 User-Agent。
- 对 Neon 的迁移和写入逐项确认。

## 12. 浏览器扩展(MVP 之后单独集成)

MVP 不做扩展,但接口按"扩展可直接接入"设计,以后只加客户端、不改后端流程:
- 队列接口返回结构化草稿:博客评论按 WordPress 标准字段 `author / email / url / comment` 给值;表单给"字段名 → 值"。
- 扩展只做三件事:领取下一条(`GET /api/queue/next`)、在目标页填入字段、我点提交后回传结果(`POST /api/candidates/{id}/submission`)。
- 扩展不点提交、不处理验证码;页面内容仍视为不可信输入。
- 本机单用户阶段用一个本机 token 认证扩展请求,不做账号体系。
